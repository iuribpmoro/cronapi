How to Make Scheduled HTTP Requests Without Managing Infrastructure

March 31, 2026 7 min read scheduled HTTP requests cron devops

If you've ever maintained a crontab on a production server, you know the pain. The job silently fails at 3 AM, there's no alert, and you find out when a customer emails you the next day. Or you SSH into the box, tweak the schedule, and realize two weeks later you edited the wrong server's crontab.

Running your own cron infrastructure is a solved problem — just not a fun one. This post shows you a simpler path: scheduled HTTP requests via a dedicated API, with no servers to manage, full execution history, and automatic retries.

The Problem With Traditional Cron

Linux's crontab was designed in the 1970s for local shell commands. For modern API-first applications, it creates real friction:

  • Cron is tied to a server. When that server goes down, your jobs stop. When you scale horizontally, you have to pick exactly one node to run cron — or deal with duplicate execution.
  • No built-in monitoring. Did the job run? Did it succeed? You have to build this yourself — typically by parsing syslog or wrapping every command in a custom logging script.
  • No retries. If your endpoint is temporarily down at 2 AM, that execution is gone. Cron doesn't retry.
  • Debugging is painful. When a cron job fails, you get an email (if you configured MAILTO) or nothing. There's no request history, no HTTP status code, no response body.

A Better Approach: Scheduled HTTP Requests via API

Instead of running a cron server, you register a scheduled HTTP request with a dedicated scheduling API. You tell it:

  1. Which URL to call
  2. On what schedule (cron expression)
  3. What HTTP method and headers to use

The API handles the rest: firing the request, capturing the response, retrying failures, and logging every execution. Your application only needs to expose an HTTP endpoint — which you probably already have.

2. Schedule your first HTTP request

Schedule a POST to your application endpoint every hour:

curl -X POST https://cronapi.up.railway.app/api/v1/jobs \
  -H "Authorization: Bearer cron_live_aBcDeFgHiJ..." \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Hourly data sync",
    "endpointUrl": "https://myapp.example.com/api/cron/sync",
    "cronExpression": "0 * * * *",
    "httpMethod": "POST",
    "headers": {
      "Content-Type": "application/json"
    },
    "body": "{\"source\": \"scheduler\"}"
  }'

That's it. CronAPI will fire a POST request to your endpoint every hour, capture the HTTP response, and make it available in your execution history.

3. Check execution history

curl https://cronapi.up.railway.app/api/v1/jobs/job_abc123/executions \
  -H "Authorization: Bearer cron_live_aBcDeFgHiJ..."

You'll see every execution with its status, HTTP response code, response body, and duration in milliseconds.

Handling Failures Gracefully

Scheduled HTTP requests fail for many reasons: network timeouts, service restarts, deployment windows. CronAPI retries failed requests automatically with exponential backoff — 3 attempts before marking an execution as failed.

To make your endpoint resilient to retries, implement idempotency using the execution ID that CronAPI passes in the X-CronAPI-Execution-Id request header:

// Express.js example
app.post('/api/cron/sync', async (req, res) => {
  const executionId = req.headers['x-cronapi-execution-id'];

  // Check if we've already processed this execution
  const alreadyProcessed = await redis.get(`exec:${executionId}`);
  if (alreadyProcessed) {
    return res.json({ status: 'already_done' });
  }

  // Do the work
  await runSync();

  // Mark as processed (expire after 24h to avoid unbounded growth)
  await redis.setex(`exec:${executionId}`, 86400, '1');

  res.json({ status: 'done' });
});

Securing Your Scheduled Endpoints

Your webhook endpoint is reachable from the internet. Without authentication, anyone can trigger your scheduled jobs by hitting the URL directly.

CronAPI signs every request with HMAC-SHA256. Verify the signature before processing:

const crypto = require('crypto');

const CRONAPI_SECRET = process.env.CRONAPI_WEBHOOK_SECRET;

app.post('/api/cron/sync', (req, res, next) => {
  const sig = req.headers['x-cronapi-signature'];
  const expected = 'sha256=' + crypto
    .createHmac('sha256', CRONAPI_SECRET)
    .update(req.rawBody) // needs raw body middleware
    .digest('hex');

  if (!crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected))) {
    return res.status(401).json({ error: 'signature mismatch' });
  }

  next();
});

Tip: Store your webhook secret in an environment variable, not in code. Rotate it if it's ever exposed.

Migrating From a Cron Server

If you're currently running cron jobs on a server, migration is straightforward:

  1. Identify HTTP-callable jobs. Any cron job that calls a URL (curl, wget, HTTP client) can be moved directly.
  2. Wrap shell-only jobs. For jobs running local scripts, expose a thin HTTP endpoint that runs the same logic.
  3. Register jobs with CronAPI. One API call per job. Match the cron expression from your crontab.
  4. Run in parallel for one cycle. Keep the crontab running and watch both execution logs to confirm matching behavior.
  5. Remove the crontab entries. Once you're confident, delete the old crontab lines and decommission the scheduling server.

Most teams complete this migration in an afternoon. The main work is exposing HTTP endpoints for any jobs that were pure shell commands.
